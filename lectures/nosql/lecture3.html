1.1 Introduction

1.1 Introduction : pourquoi le cloud ?

Les volumes de données augmentent, et les entreprises veulent des solutions plus flexibles et plus efficaces.

Système traditionnel

Serveurs achetés à l’avance, dimensionnés pour le pic, installés et maintenus sur place.

Plateforme cloud

Ressources élastiques : on augmente ou on réduit selon le besoin, et le cloud prend en charge SQL (MySQL, PostgreSQL) comme NoSQL (MongoDB, DynamoDB).

Idée clé : le cloud n’est pas un type de base de données. C’est une façon de fournir des bases (et des serveurs, du stockage, des logiciels) via Internet.
1.2 Qu’est-ce que le cloud computing ?

1.2 Qu’est-ce que le cloud computing ?

Accéder à des ressources informatiques (serveurs, stockage, bases de données, logiciels, services) via Internet, sans les posséder physiquement.

Pourquoi “cloud” ?

Dans les schémas informatiques, Internet est dessiné sous forme de nuage : une infrastructure décentralisée et invisible derrière les services.

Histoire

Issu de l’évolution de la virtualisation et des réseaux, popularisé au début des années 2000.

1.2 · Caractéristiques

Caractéristiques clés du cloud

1. Accès à distance

Depuis n’importe quel appareil connecté. Favorise le travail collaboratif entre équipes dispersées.

Exemple consulter ses fichiers ou une application métier depuis un navigateur.

2. Élasticité

Augmenter ou réduire la capacité automatiquement et instantanément selon la demande.

Exemple un site e-commerce qui monte en charge pendant le Black Friday, puis redescend.

3. Paiement à l’usage

Modèle “pay-as-you-go” : on paie seulement ce qu’on consomme, sans gros investissement initial.

Exemple 1 To stocké = on paie 1 To ; si on passe à 2 To, la facture change.
Ces trois caractéristiques rendent le cloud flexible, économique et adapté aux besoins évolutifs.
1.2 · Élasticité

Élasticité : suivre la demande

La capacité (courbe bleue) suit la demande (courbe orange) : on paie la ressource quand on en a besoin, pas en permanence.

Lecture : quand la courbe bleue se superpose à l’orange, les ressources sont bien dimensionnées. Trop haut = coût inutile ; trop bas = service dégradé.
1.3 Architecture du cloud

1.3 Architecture : front-end et back-end

Front-end (interface)

La partie visible par l’utilisateur final : navigateur, application, interface graphique.

Back-end (infrastructure)

Gère les ressources, les services et les bases de données qui soutiennent les opérations.

Schéma à retenir : Client → Internet → Back-end. Le client ne voit que l’interface, pas les serveurs derrière.

1.2 · Modèles de service

Les trois modèles de service

Plus on monte dans la pile, plus le fournisseur gère de choses à votre place.

SaaS

Utiliser un logiciel en ligne.
Ex. : Gmail, Zoom, Google Docs

PaaS

Développer une application sans gérer l’infrastructure.
Ex. : Heroku, Google App Engine

IaaS

Louer une infrastructure complète pour héberger vos outils.
Ex. : Amazon EC2

1.4 Bases de données dans le cloud

1.4 Une base de données “dans le cloud”

Une base hébergée sur des serveurs distants (AWS, Azure, Google Cloud), accessible via Internet ou un réseau privé sécurisé.

A/ Accessibilité mondiale

Données accessibles de n’importe où avec Internet, travail collaboratif et accès en temps réel.

Avec MongoDB Atlas

Connexion via navigateur ou MongoDB Compass depuis n’importe quel endroit connecté.

1.4 · Scalabilité

Scalabilité : verticale ou horizontale ?

Horizontale

Ajouter de nouveaux serveurs pour répartir la charge et gérer un volume croissant de données. C’est la voie privilégiée du cloud et de NoSQL (sharding).

Verticale

Améliorer les performances d’un serveur existant (mémoire, processeur). Simple, mais limitée par la taille maximale de la machine.

1.4 · Coûts & disponibilité

Réduction des coûts et haute disponibilité

C/ Réduction des coûts

Plus besoin d’acheter des serveurs physiques ni d’assurer leur maintenance. Le fournisseur gère infrastructure, mises à jour et réparations.

Résultat : dépenses d’infrastructure réduites, service performant.

D/ Haute disponibilité

Redondance sur plusieurs data centers : en cas de panne d’un serveur, les données restent accessibles ailleurs.

1.4 · Sécurité

E/ Sécurité

Les fournisseurs proposent des solutions avancées pour protéger les données sensibles.

Chiffrement

Les données sont chiffrées en transit (réseau) et au repos (disque) : impossible à lire en cas de compromission.

Authentification forte

Authentification multi-facteurs, clés API, identifiants robustes : seuls les utilisateurs autorisés accèdent à la base.

Règles IP

Restreindre l’accès à certaines adresses IP pour bloquer les connexions non autorisées.

Sauvegardes régulières : elles évitent la perte de données, même si tout le reste échoue.
1.5 Étude comparative · définitions

1.5 SGBD parallèles et systèmes clouds

SGBD parallèles

Plusieurs processeurs ou machines exécutent les tâches en parallèle pour traiter de très grandes quantités de données. Architecture souvent MPP (Massively Parallel Processing).

Systèmes clouds

Environnements virtuels qui fournissent stockage et puissance de calcul via Internet. Exemples : MongoDB Atlas, Amazon DynamoDB.

Exemples cités : Teradata (fondé en 1979, entrepôts de données, MPP) et Greenplum (base parallèle open source basée sur PostgreSQL, pour le Big Data).

1.5 Cas d’utilisation · Conclusion

Quand utiliser quoi ?

SGBD parallèles

Environnements où les performances locales sont cruciales : centres de données de banques, analyses scientifiques.

Systèmes cloud

Applications à collaboration mondiale : SaaS (Zoom, Google Workspace), e-commerce (Amazon, eBay, Etsy, AliExpress).

Conclusion : SGBD parallèles et cloud ne sont pas concurrents mais complémentaires. Une solution hybride combine les deux, en profitant des points forts de chacun : performance et contrôle local, flexibilité et accessibilité du cloud.
Révision

Auto-évaluation

1. Quelle est la différence entre front-end et back-end ?

Le front-end est la partie visible par l’utilisateur (interface). Le back-end gère les ressources, services et bases de données.

2. Que signifie l’élasticité ?

La capacité d’augmenter ou de réduire automatiquement les ressources selon la demande.

3. Quelle est la différence entre scalabilité horizontale et verticale ?

Horizontale : ajouter des serveurs. Verticale : rendre un serveur plus puissant.

4. Dans quel modèle le fournisseur gère-t-il aussi l’OS et le runtime, mais pas votre application ?

PaaS : vous développez et déployez, le fournisseur gère la plateforme.

5. Citez deux mesures de sécurité d’une base dans le cloud.

Chiffrement (en transit et au repos), authentification multi-facteurs, règles IP, sauvegardes.

Fin

Ce qu’il faut retenir

Cloud

Ressources via Internet, élastiques, paiement à l’usage, accessibles partout.

Services

SaaS = utiliser · PaaS = développer · IaaS = louer l’infrastructure.

BDD cloud

Scalabilité horizontale, haute disponibilité par réplication, chiffrement et contrôle d’accès.

Comparaison

Parallèle = performance locale et contrôle ; cloud = flexibilité et accessibilité ; souvent les deux (hybride).
